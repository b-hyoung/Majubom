## 바로 보기와 GPU 실행

작업실 상단의 3D 공간 모니터를 엽니다. 처음에는 침대 위에서 움직이는 **DEMO / SIMULATED 관절**을 보여 줍니다. 카메라 2D 관절에 임의 깊이를 붙인 결과가 아니며, 실제 추적/저장/자세 판정에 사용하지 않습니다. DEMO 체크를 끄면 실제 보정된 3D만 표시하고, 미보정이면 관절을 숨깁니다.

Windows의 RTX GPU 경로는 기존 MediaPipe Web GPU delegate와 Chrome/Edge의 D3D11을 사용합니다. CUDA/PyTorch 경로로 바꿨다는 뜻이 아닙니다. 저장소에서 다음처럼 준비/실행합니다.

```powershell
python -m pip install -e ".[live,stereo]"
cd tools/gpu-preview
npm ci
cd ../..
python -m bed_pose live --pose-device browser_gpu --pose-max-people 1
```

관절 모델은 기존 `checkpoints/pose_landmarker_full.task` 또는 작업실에서 선택한 모델을 사용합니다. GPU 브리지는 저장소의 `tools/gpu-preview`와 그 npm 의존성이 필요합니다. Python wheel만 설치한 저장소 밖의 GPU 실행은 별도 패키징 대상입니다. 실패하면 CPU/합성 결과로 몰래 대체하지 않고 오류를 표시합니다.

`--pose-max-people 1`은 단일 대상용 선택 옵션입니다. 내부 단일 인물 추적/평활화를 사용할 수 있지만 주변 인물을 추가 검출하지 못할 수 있습니다. 화면의 인원 수만으로 다인 장면이 아니라고 보장할 수 없습니다. 실제 복원 때 운영자가 양쪽에 같은 사람 한 명만 있도록 유지해야 합니다. 기존 최대 3명 동작은 옵션 생략 또는 `--pose-max-people 3`으로 유지합니다. CLIP 경로는 제거하거나 바꾸지 않았으며 이번 카메라 연결에서는 선택하지 않았습니다.

## 속도 변경과 측정 해석

- 기존 화면의 요청 후 350ms 대기를 25ms로 줄이고, 상태·입력 요약·두 영상을 한 번에 받는 `/api/room/live`를 추가했습니다. 큰 판정 프로필 전체를 매번 전송하지 않으며 같은 프레임의 JPEG를 재전송하지 않습니다. HTTP/1.1 연결을 재사용합니다.
- GPU 브리지의 프레임 전송은 Base64/stdio/CDP 왕복 대신 로컬 바이너리 HTTP 지속 연결을 사용합니다. 초기 버전에서 반복 연결 시간 초과가 실제 발생했고, 지속 연결로 수정 후 연속 동작을 확인했습니다. RGB/모델은 로컬에만 전달됩니다.
- Three.js는 `powerPreference=high-performance`, 17개 관절의 InstancedMesh, 동적 선 버퍼, 재사용 행렬을 사용합니다. 매 관측마다 스켈레톤/재질/지오메트리를 폐기/재생성하지 않습니다. 픽셀 비율 상한은 1.5입니다.
- 실제 관절 표시는 렌더링 프레임 사이에 시간 상수 35ms의 인과적 지수 보간을 합니다. 표시 지연이 조금 생기며 미래 관측을 쓰지 않습니다. 이 보간을 추론 FPS나 새로운 실제 관절 측정으로 세지 않습니다.
- 화면에 3D 렌더링 FPS, 카메라 A/B별 새 영상 반영 FPS, 기존 추론 처리 FPS와 실행 장치를 따로 표시합니다. 숨겨진 탭/백그라운드, 사람 수·가림·다른 프로그램·카메라 드라이버·노출 설정에 따라 달라집니다. GPU 사용률 100%나 고정 FPS를 보장하지 않습니다.

이번 RTX 5070 Laptop GPU에서 실제 delegate renderer가 NVIDIA/D3D11인 것을 확인했습니다. 브라우저 데모 렌더링은 관찰 시 약 165FPS였고, 두 카메라의 GPU 처리는 관찰 구간/부하에 따라 약 15~30FPS였습니다. 최종 1인 모드 점검에서 C920은 약 30FPS, USB2.0 카메라는 약 15FPS였고, 후자는 프레임 수신 자체가 약 64ms 간격이었습니다. GPU 관절 계산은 해당 표본에서 각각 약 14/16ms였습니다. 드라이버의 30FPS 보고값을 실제 수신 FPS로 간주하지 않습니다. 별도 90초 확인의 각 표본에서 두 스트림 오류 없이 프레임 ID가 증가했습니다(`outputs/gpu-live-health.json`, 로컬 검사 자료). 이는 수 시간 안정성·정확도 검증이 아닙니다. 최초 고정 이미지 비교에서는 CPU 약 22ms와 초기 GPU 전송 경로 약 30ms였으므로, GPU가 항상 빠르다고 주장하지 않습니다. 지속 연결과 1인 옵션의 실제 성능은 현재 화면의 별도 지표로 확인하세요.

## 보정 방식

3D 화면 아래 **카메라 보정 → 보정 방식**에서 선택합니다.

| 방식 | 입력과 출력 | 실제 방 3D 적용 |
|---|---|---|
| 화면 ChArUco | 마커 ID가 있는 격자, 실제 표시 폭, 공통 코너 8개 이상/쌍, 10쌍 이상 | 방 정렬 실측 후 적용 |
| 화면 체커보드 | 내부 코너 수, 실제 표시 폭, 10쌍 이상 | 방 정렬 실측 후 적용 |
| 화면 ArUco | ID가 있는 마커 격자, 실제 표시 폭, 공통 코너 8개 이상/쌍, 10쌍 이상 | 방 정렬 실측 후 적용 |
| 실측 기준점 | 알려진 내부값/왜곡, 방 기준점 6개 이상과 원본 픽셀 대응/카메라, 선택적 카메라 실측 위치 | PnP·오차 검사를 통과한 후보만 적용 |
| 자연 특징점 | 알려진 내부값/왜곡, 정적인 겹치는 장면 | 척도 없는 상대 자세만 출력. 적용 차단 |
| 수동 카메라 배치 | 위치 XYZ와 바라보는 점 XYZ | 시각화 전용 화살표. 보정으로 사용하지 않음 |

### 화면 ChArUco/체커보드/ArUco

1. 보정 방식을 고르고 **화면 패턴 열기**를 누릅니다. `/screen-pattern?kind=charuco&columns=9&rows=6` 같은 페이지입니다. ChArUco와 ArUco는 OpenCV `DICT_4X4_1000`을 사용합니다. 체커보드/ChArUco의 수는 내부 코너 수, ArUco의 수는 마커 열/행 수입니다.
2. 다른 모니터·노트북·휴대폰 화면에 패턴을 표시합니다. **휴대폰용 HTML 저장**은 PNG가 내장된 HTML을 저장합니다. 다른 기기로 옮겨 열면 인터넷/외부 자산 없이 표시할 수 있습니다. 루프백 서버를 LAN에 노출하거나 카메라 영상을 외부에 전송하지 않습니다.
3. 최종 표시 크기/전체 화면/배율/기기 방향을 정한 뒤 **바깥 흰 여백을 제외한 전체 격자 이미지 가로**를 자로 측정합니다. 보정 UI의 실제 패턴 가로(mm)에 입력하고 **패턴 설정 저장**을 누릅니다. 패턴 페이지의 mm 입력은 안내용이며 서버 설정을 자동 변경하지 않습니다. 화면 크기 변경 시 다시 측정해야 합니다. CSS mm, 기기 사양, 픽셀 수로 물리 크기를 추측하지 않습니다.
4. 두 카메라가 **같은 화면 면**을 동시에 보게 합니다. 평면 화면의 반대쪽에서는 같은 패턴을 볼 수 없습니다. 카메라 설치/패턴 위치에 공통 시야가 없으면 배치나 별도 표시 기기를 조정해야 합니다. 크기가 작은 휴대폰은 멀리서 충분한 코너가 잡히지 않을 수 있습니다.
5. 화면을 잠시 정지시키고 **공통 패턴 촬영**을 누릅니다. 중앙/가장자리, 여러 위치·거리·기울기에서 10쌍 이상 저장합니다. 같은 시점 반복 촬영만으로 좋은 보정이 보장되지 않습니다. 반사·낮은 대비·초점 흐림·모아레·주사/노출 줄무늬·롤링셔터를 확인하세요. 체커보드는 양쪽의 물리 코너 순서도 확인해야 합니다.
6. **기준 촬영 쌍**을 선택하고 **보정 계산**을 실행합니다. 내부/스테레오 보정 및 왜곡 계수·재투영 오차를 계산합니다. 결과의 승인된/제외된 촬영과 이유, RMS, 행렬은 후보 원본에서 확인할 수 있습니다. 계산은 별도 스레드에서 진행해 작업실 잠금을 오래 잡지 않습니다.

**화면은 방 바닥이 아닙니다.** 기준 촬영 때의 실제 패턴→방 회전/이동을 알고 있을 때만 JSON으로 넣습니다. 회전은 오른손 3×3 정규 회전, 이동은 방 좌표 미터이며 `measured:true`가 필요합니다. 체커보드 원점은 첫 내부 코너, ChArUco/ArUco는 OpenCV 보드 바깥 기준 원점입니다. 보드 좌표의 X는 오른쪽, Y는 아래쪽이며 실제 설치에 맞는 회전이 필요합니다. 임의로 Y-up이라고 가정하지 않습니다.

방 변환을 생략하면 **target_world**의 미터 단위 보정 후보만 생성합니다. 화면을 바닥으로 자동 간주하거나 침대 중심에 임의 배치하지 않습니다. `room_world` 정렬이 없으면 적용 버튼이 비활성화되고 백엔드 검증도 적용을 거부합니다. 실제 정답 좌표로 별도 확인한 정확도는 아닙니다.

촬영은 `recordings/live/.monitor/captures/`의 PNG/메타데이터로 저장합니다. 패턴 종류·코너 수·실측 폭·카메라 바인딩이 달라진 촬영을 혼합하지 않습니다. 서로 다른 해상도는 현재 보정 도구에서 지원하지 않습니다. 후보는 `.monitor/calibration-candidate.json`, 적용값은 `calibration.json`, 방식/실측 설정은 `setup.json`에 보관합니다.

### 실측 기준점과 카메라 위치

UI의 **입력 형식 보기**로 JSON 구조를 얻습니다. 실제 내부 행렬·왜곡 계수·해상도를 채우고 카메라별 `world_points_m`, `image_points_px`에 같은 물리점의 순서대로 대응을 넣습니다. 각 카메라 6점 이상, 일직선이 아닌 기준점이 필요하며 가능하면 서로 다른 높이/깊이의 점을 포함하세요. 픽셀은 미리보기 축소/회전 좌표가 아니라 보정 해상도의 원본 좌표입니다.

`solvePnPRansac`와 LM 보정, 전체 기준점 재투영 오차, 카메라 앞쪽 여부를 검사합니다. `measured_camera_position_m`을 주면 계산된 `-Rᵀt`와 비교합니다. 초기 전체 RMS 한계 3px/카메라 위치 차이 0.2m는 미검증 정책값이며 정밀도 보장이 아닙니다. 위치만 입력하고 렌즈 내부값/방향 근거가 없으면 검증된 외부 보정으로 취급하지 않습니다.

### 자연 특징점 상대 자세

실제 영상 해상도와 일치하는 알려진 내부 행렬/왜곡이 필요합니다. SIFT·비율 매칭, 왜곡 제거, Essential RANSAC, recoverPose로 상대 R과 이동 방향을 구합니다. 낮은 대응/인라이어 비율·평면 장면 우세·시차 부족은 실패로 표시합니다. 결과에 대응 수·인라이어 수·호모그래피 비율·정규화 좌표 Sampson 잔차를 기록합니다. 이 잔차는 픽셀/미터 오차가 아닙니다.

**실제 기준선 길이와 방 정렬을 구하지 않습니다.** 결과는 `relative_pose_unscaled`, `unit:null`, `room_alignment_verified:false`이며 실제 방 3D 적용이 차단됩니다. 미보정 K를 임의로 가정하는 경로도 없습니다.

### 수동 배치

예시 위치를 불러오거나 실제 측정한 카메라 위치와 바라보는 점을 입력해 화살표로 표시합니다. 보정 파일이 있으면 그 R/t/K 표시를 우선합니다. 수동 위치는 설치 계획/초기 시각화용이고 내부값·왜곡·정밀 회전을 인증하지 않습니다. 수동 값으로 실제 관절 삼각측량을 실행하거나 미보정 상태를 해제하지 않습니다.

## 인터페이스와 검증

기존 `/api/room/status`, 설정/캡처/보정 업로드 API를 유지합니다. 추가 인터페이스는 GET `/api/room/live`, GET `/screen-pattern`, POST `/api/room/setup`, `/api/room/solve`, `/api/room/apply-candidate`입니다. 실제 촬영은 기존 수신 시각 기준 쌍이며 노출 동기화를 뜻하지 않습니다. 같은 사람 확인·해상도·최신성·관절 가시성·시차·재투영 검사도 유지합니다.

추가 검사에서 생성한 세 패턴 검출, 실제 폭에 따른 3D 대상 좌표, 누락 실측값 거부, 화면 기준/방 기준 후보 분리, 합성 실측점 PnP와 잘못된 카메라 위치 거부, 합성 자연 특징 상대 자세의 무척도 유지, 실패 상태·수동 값의 보정 미승격, 접근 제어·가벼운 상태 전송을 확인했습니다. 합성 입력 검사와 실제 카메라 정확도 검증은 구분합니다. TypeScript/Vite build, wheel 패키징도 확인했습니다.
