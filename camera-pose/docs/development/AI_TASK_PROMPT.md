# AI에게 작업을 맡길 때 쓰는 프롬프트

[문서 목차](../README.md) · [분야 목차](README.md) · [현재 상태](../PROJECT_STATUS.md)


[프로젝트 홈](../../README.md) · [AI 공통 지침](../../AGENTS.md) · [진행 현황](../PROJECT_STATUS.md) · [로드맵](../../ROADMAP.md)

Codex 등 AI에게 프로젝트 설명을 매번 반복하지 않고 작업을 맡기기 위한 문서입니다. **아래 프롬프트 중 필요한 것을 복사하고, `[대괄호]`를 이번 작업 내용으로 바꾸면 됩니다.**

| 문서 | 역할 |
|---|---|
| [AGENTS.md](../../AGENTS.md) | AI가 읽을 프로젝트 맥락·공통 작업 원칙 |
| 이 문서 | 사용자가 복사해 전달하는 작업 요청 양식·예시 |
| [진행 현황](../PROJECT_STATUS.md) | 현재 완료한 것과 아직 시작하지 않은 것 |

예시는 요청을 작성하기 위한 자료입니다. AI가 이 문서를 읽었다고 해서 예시의 작업을 모두 수행하는 것은 아닙니다.

## 가장 간단하게 시작하기

저장소에 접근할 수 있는 AI에게 아래 내용을 전달합니다.

```text
저장소: https://github.com/zntks1234/bed-pose-skeleton-ai

AGENTS.md와 docs/development/AI_TASK_PROMPT.md를 먼저 읽고,
진행 현황·결정 사항·요구사항·로드맵에서 이번 작업과 관련된 내용을 확인해줘.

이번 작업: [원하는 작업을 구체적으로 작성]
완료 기준: [어떤 결과를 확인하면 완료인지 작성]

현재 단계와 보류 사항을 유지하면서 필요한 작업을 수행하고,
변경 파일·실제 확인 결과·남은 미정 사항을 한국어로 알려줘.
```

**저장소에 접근할 수 없는 AI라면:** `AGENTS.md`, `PROJECT_STATUS.md`, `DECISIONS.md`, `REQUIREMENTS.md`, `ROADMAP.md`와 작업 관련 상세 문서를 함께 첨부하거나 내용을 붙여 넣습니다. 링크를 전달한 것과 AI가 내용을 실제로 읽은 것은 구분합니다.

## 상세 작업 요청 양식

새 AI에게 처음 맡기거나 작업 범위를 명확히 정할 때 사용합니다.

```text
너는 '카메라 기반 침대 자세·움직임 분석 AI' 프로젝트를 돕는 AI다.
저장소: https://github.com/zntks1234/bed-pose-skeleton-ai

[프로젝트 목적]
카메라로 침대 자세·움직임을 독립 분석하고,
외부 ToF·mmWave 시스템의 결과와 같은 시간대에 비교한다.
두 시스템의 일치도와 실제 정답 기준 정확도를 구분한다.

[먼저 확인할 자료]
AGENTS.md, README.md, docs/PROJECT_STATUS.md,
docs/DECISIONS.md, docs/REQUIREMENTS.md, ROADMAP.md를 읽어라.
그다음 이번 작업과 관련된 설계·측정·평가·기술·논문 문서를 읽어라.
과거 대화를 알고 있다고 가정하지 말고 실제 파일과 현재 환경을 확인해라.
읽을 수 없는 자료는 그 사실을 밝혀라.

[이번 작업]
- 작업 유형: [조사 / 설계 / 구현 / 수정 / 검증 / 문서 정리]
- 목표: [이번에 해결할 문제 또는 추가할 결과]
- 작업 범위: [대상 기능·파일·논문 ID·요구사항 ID 등]
- 이번에 하지 않을 일: [보류할 기능이나 범위]
- 제공 자료와 환경: [영상·센서 출력 형식·촬영 조건 등, 없으면 '미제공']
- 산출물: [작성·수정할 코드·문서·표·실험 기록 등]
- 완료 기준: [재현 방법·확인할 동작·검증 조건]

[유지할 원칙]
계획 목표·카메라 예측·센서 결과·실제 정답을 분리해라.
목표 자세와 외부 센서 결과를 카메라 예측 입력으로 사용하지 마라.
자세·점유 상태·이탈/복귀 이벤트·판정 불가를 구분해라.
합의·잠정·미정·보류 상태를 유지하고, 후보 기술을 확정 기술로 쓰지 마라.
논문 보고값·적용 제안·자체 실험 결과와 각각의 검증 범위를 구분해라.
본문 미확인 논문은 명확히 표시하고 서지만 유지해라. 초록·검색 요약의 연구 주장·효과·성능은 사실 판단, 기술·모델 선정 근거에서 제외해라.
공개판을 확인하고 최종판을 확인하지 못했다면 판본을 분리해 미확인 최종판의 결과를 주장하지 마라.
원본 영상·개인정보·학습/평가 데이터는 GitHub에 올리지 마라.

[진행 방식]
이번 요청의 범위와 완료 기준을 짧게 정리한 뒤 수행해라.
이미 문서에 답이 있는 질문을 반복하지 말고 기존 결정을 활용해라.
필수 조건이 없으면 필요한 정보만 질문하고 독립적으로 가능한 작업은 진행해라.
임시 가정은 표시하고 합의된 사양으로 기록하지 마라.
기존 변경 사항을 보존하고, 새 결정이나 진행 변화는 관련 문서에 반영해라.

[완료 보고]
변경 내용과 이유, 변경 파일, 실제 검증 결과,
수행하지 못한 검증과 남은 결정 사항을 한국어로 간결하게 알려줘.
문서 작성·구현·모의 실행·실제 환경 검증을 구분해서 보고해라.
```

작업 유형이 **설계**라면 설계 산출물까지, **구현**이라면 구현과 가능한 동작 확인까지가 요청 범위입니다. 한 번에 모든 개발 단계를 맡기기보다 로드맵의 한 단계나 요구사항 한 묶음으로 범위를 정합니다.

## 현재 프로젝트에 맞는 작업 예시

아래 예시는 상세 양식의 **이번 작업** 부분에 넣을 수 있습니다. 기술·장비·라벨이 미정인 항목은 그대로 표시합니다.

### 예시 1 · 기존 후보 비교 실험 계획 보완

```text
작업 유형: 설계
목표: docs/research/POSE_BENCHMARK_PLAN.md의 기존 계획을 확인된 촬영 조건과 자료에 맞춰 보완.
선행: 진행 현황·결정 사항·기존 비교 실험 계획을 읽고 추가로 확인된 조건 파악.
범위: 같은 저장 영상에서 MediaPipe Pose Landmarker·YOLO Pose·RTMPose를
비교하는 계획을 유지하고 MoveNet을 경량 대안으로 유지.
산출물: 기존 계획에서 달라진 입력 자료·환경, 관절 매핑 검수 항목,
실행 순서·지표·완료 기준과 아직 준비되지 않은 조건.
제외: 모델 최종 선정, 실험하지 않은 성능 수치 작성, 모바일 기능 구현.
완료 기준: 장비·영상이 준비되면 같은 조건으로 비교할 수 있고,
정답이 없어 아직 계산할 수 없는 지표와 준비가 필요한 항목이 표시되어 있음.
```

### 예시 2 · 동일 영상 스켈레톤 비교 러너 구현 (다음 작업)

```text
작업 유형: 구현
목표: docs/research/POSE_BENCHMARK_PLAN.md의 9장에 정의된 기존 비교 러너의 미완성 평가·실험 기능 검토/확장.
선행: AGENTS.md, ROADMAP.md, docs/design/DATA_AND_VALIDATION.md,
      docs/research/TECHNOLOGY_CANDIDATES.md, docs/research/POSE_BENCHMARK_PLAN.md 읽기.
범위: 동일 저장 영상의 프레임·PTS 입력 → PoseEstimatorAdapter → 원본 관절 출력
      → 공통 COCO17 매핑 → 미검출·건너뜀 포함 프레임별 기록 → 기초 통계.
원칙: 추론 실행 위치·방식은 확정하지 말 것. 모델 선택은 같은 영상의 실험 결과를 근거로 할 것.
      모듈 분리·불필요한 연산 회피·정확한 시간 기록은 필수.
출력: 재현 가능한 실행 명령, 버전·가중치 기록, manifest/JSONL/보고서,
      관절 순서/좌우/결측/PTS/실패 테스트.
제외: 자세 분류·이탈 최종 모델, 외부 센서 연동, 모바일 UI, 실제 점수 날조.
완료 기준: 동일 영상 재실행 결과가 프레임 ID와 함께 재현되고,
      정답 데이터가 없으면 정확도 관련 지표를 '계산 불가'로 보고.
```

### 예시 3 · 정해진 범위의 최소 기능 구현

```text
작업 유형: 구현
목표: [요구사항 ID와 이번에 구현할 한 가지 기능]
범위: [대상 입력·화면·분석·저장 동작]
환경과 기술: [확인된 개발 실행 환경·입력 영상/카메라·모델, 미정인 것은 미정으로 표시]
산출물: 구현 코드, 확인한 설치·실행 방법, 관련 문서 갱신.
제외: 이번 기능과 관계없는 확장, 모바일 웹 원격 제어,
외부 센서 값이나 계획 목표를 카메라 예측에 사용하는 기능.
완료 기준: [입력]을 넣으면 [관찰 가능한 동작·출력]을 확인할 수 있음.
미검출·잘못된 입력 등 관련 실패 동작도 확인하고,
실제 카메라 확인과 모의 입력 확인을 구분하여 보고.
필수 기술이 미정이면 필요한 선택지를 좁히고, 영향을 받지 않는 작업부터 진행.
```

### 예시 4 · 논문 근거 확인 및 기존 문서 반영

```text
작업 유형: 검증 및 문서 정리
목표: [논문 ID·제목]의 기존 요약을 원문과 대조해 해당 항목을 수정.
범위: 방법, 입력·정답, 데이터·분할, 실험 조건·표·지표, 한계.
산출물: 확인한 판본과 절·표 근거를 포함한 기존 논문 항목의 수정.
필요하면 논문 색인·기술 후보 문서의 관련 설명도 맞춤.
제외: 초록만으로 세부 결과 확정, 논문 성능을 우리 환경 성능으로 표현,
원자료 없이 서로 다른 수치 중 하나를 정답으로 단정.
완료 기준: 확인 사실·프로젝트 적용 제안·확인하지 못한 내용이 구분되어 있음.
본문을 확보하지 못하면 **‘본문 미확인 · 사실 판단 제외’**로 표시하고 서지만 남겨라. 초록의 방법·성능은 기술 선정·설계 근거로 사용하지 마라. 검증한 공개판 내용은 미확인 최종판으로 전용하지 마라.
```

## 문서를 계속 활용하는 방법

- **매번 바꿀 것:** 이번 작업의 목표·범위·자료·산출물·완료 기준.
- **현재 상태를 확인할 곳:** [진행 현황](../PROJECT_STATUS.md)과 실제 코드. 진행 상태를 이 문서에 반복해서 복사하지 않습니다.
- **새 합의를 기록할 곳:** [결정 사항](../DECISIONS.md). 공통 작업 원칙이 달라지면 [AGENTS.md](../../AGENTS.md)도 함께 갱신합니다.
- **요청문을 작성할 때:** '완성해줘'처럼 범위가 큰 문장보다 '어떤 입력에서 어떤 결과를 확인할지'를 적습니다.
