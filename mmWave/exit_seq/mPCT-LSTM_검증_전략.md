# mPCT-LSTM 논문 검증 + 우리 전략

> 2026-07-05 · 실물 PDF(Digital Signal Processing 164, 2025, 105263) 정독 결과.
> 예전엔 페이월로 스니펫만 봐서 "미검증"이라 표시했던 걸, **실물 읽고 확정**함.
> 결론 한 줄: **"공간→LSTM 시간" 뼈대는 우리랑 동일·SOTA 확인. 단 침대도 아니고 우리 칩도 아니라 결과·근거로는 못 씀. 방법(구조)만 참고.**

---

## 1. 논문 기본
- **제목**: mPCT-LSTM — 경량 mmWave 3D 점군 행동인식(HAR) 모델
- **출처**: Digital Signal Processing 164 (2025) 105263, Elsevier · Xuning Wang 외 (중국 장쑤과기대)
- **목적**: 희소 mmWave 점군을 **라즈베리파이에서 돌릴 만큼 가볍게** HAR

## 2. 예전 질문 3개 — 실물로 확정
| 질문 | 답 (실물 확인) |
|---|---|
| 침대에서 한 거? | ❌ **아니요** — 걷기·점프·복싱·스쿼트·팔제스처 (서서 하는 일반행동/손동작). 자세·이탈 아님 |
| 우리 하드웨어 동일? | ❌ **아니요** — **IWR1443 · 77GHz** (§5.1 명시). 우리는 IWR6843AOP · 60GHz. 다른 칩·대역 |
| 어떤 알고리즘? | **mPCT(공간) + LSTM(시간)** ↓ |

## 3. 알고리즘 — 우리랑 직결
```
프레임마다 점군 → mPCT(공간특징) → LSTM(시간특징) → FC → 분류
                  ↑ Embedding(FPS 128중심점 + KNN k=4)
                    + Offset-Attention 4층
```
- **mPCT** = Point Cloud Transformer 변형. 프레임 하나의 공간 특징을 학습으로 추출.
- **LSTM** = 프레임별 특징을 시간순으로 엮음.
- → **"프레임별 공간 인코더 → LSTM 시간모델" = 우리 구조와 동일 계열.**
  우리는 공간을 **수제 특징(높이·속도·위치)**, 얘넨 **학습 PCT** 로 한 차이뿐.

## 4. 결과 (검증됨)
- 평균 정확도 **97.26%** (MMActivity 98.87 / Pantomime 98.88 / mHomeGes 94.02), SOTA +1.41%
- 연산량 **0.09 GFLOPS** (70%↓), 파라미터 0.34M, 라파4B **0.135초/동작**
- 3개 **공개 데이터셋** + 5-fold CV (자기 데이터 아님, 공유 권한 없음)
- 전처리: 2초 창(60프레임 @30fps), FPS 리샘플, 슬라이딩 윈도우

## 5. 우리한테 주는 것 (정직)
**✅ 쓸모:**
1. **우리 방향 검증** — "공간→LSTM"이 희소 mmWave SOTA. 우리 실측(LSTM F1 42 > 뭉갬 13)과 같은 결론.
2. **Plan B 참고** — 수제 특징 대신 **mPCT 학습 인코더**(경량·파이 배포)로 업그레이드하는 구체 레퍼런스.
3. **전처리 참고** — 창 길이·FPS·슬라이딩 (대부분 이미 하고 있음).

**⚠️ 착각 금지:**
1. **97.26%는 우리 게 아님** — 걷기·제스처를 IWR1443·77GHz·1.2~5m 서서 한 결과. 침대·이탈·우리 칩엔 그대로 적용 안 됨.
2. **"우리 칩 일치 논문" 아님** — PNHM·Sensor-Stack(IWR6843)과 달리 다른 칩. **하드웨어 근거로 못 씀.**
3. **"침대 선행연구" 아님** — 일반 HAR.

## 6. 전략 — Phase A 유지 → 데이터 → Plan B
```
지금 (Phase A): 수제 공간특징(높이·속도·위치) → LSTM   ← 데이터 적어도 됨, 이미 함(F1 42)
   ↓  [데이터 대량 수집: 여러 명·100+ 이벤트]  ← 진짜 다음 할 일
나중 (Plan B):  학습 공간인코더(mPCT) → LSTM          ← 데이터 많이 필요, 정확도↑
```
- **뼈대(공간→LSTM)는 확정, 안 바꿈.** LSTM 부분 그대로, 앞의 공간 특징만 나중에 교체.
- **Plan B는 지금 하면 안 됨** — 논문은 12k~22k 샘플·25~41명. 우리는 569·1명·이탈17건 → 학습 인코더는 **과적합**.
- **Plan B 트리거 = 데이터 양** (여러 명·100+ 이벤트 모은 뒤).

## 7. 창 프레임 30 유지 이유 (60 안 올린 근거)
1. **30은 임의값 아님** — **PNHM(IWR6843, 우리 칩)이 30 최적 보고**. 하드웨어 일치하는 쪽을 따름.
2. **프레임 수 ≠ 시간** — 우리 센서 **~18fps**(frameCfg 55ms). → **30프레임 ≈ 1.65초**, 논문 2초와 이미 비슷. 논문 60은 30fps 기준(2초)이라, 우리 fps로 2초면 **~36프레임**이지 60 아님. (60 그대로면 우리는 3.3초 = 과함)
3. **이탈 동작이 짧음(1~2초)** — 창 너무 길면 무관 구간 섞여 신호 희석.
4. **데이터 적어 튜닝 무의미** — 창 길이는 데이터로 튜닝할 값. 쌓인 뒤 **30 vs 36 vs 45** 비교.
→ 결론: **60은 근거 없음. 실험한다면 2초=~36프레임을 데이터 쌓인 뒤 튜닝.**
